# workshop-app 全云端零运维部署架构设计

> 目标：用户入学后无人现场维护，系统在校期间（约 2–3 年）独立稳定运行。
> 约束结论：排除本地主部署（离厂后无人维护）→ 采用**全云端 + 托管容器平台**，SQLite 单文件零数据库服务。
> 状态：本文件为**架构设计 + 落地规格**；具体文件（Dockerfile / backup.js / CI 工作流）待平台确认后落入项目。

---

## 0. 决策依据

| 约束 | 推论 |
|---|---|
| 离厂后无 IT 人员 | 不能有任何需要 SSH 登录、打系统补丁、手动重启的环节 → 排除裸 ECS / 轻量服务器自管 |
| 数据在国内（工厂业务） | 排除海外平台（Railway/Render/Fly），避免数据出境与访问延迟、备案问题 |
| 并发低（15–25 人偶发写） | SQLite 完全够用，且单文件=零数据库服务运维，是零运维最优解 |
| 在校多年无人管 | 必须：自动重启 + 数据双副本（卷+对象存储）+ 外部宕机告警 + 证书/域名自动续 |

## 1. 总体架构

```
车间电脑/平板(浏览器)
      │  HTTPS（域名 + 平台托管免费 DV 证书，仅暴露 443）
      ▼
┌─────────────────────────────────────────────────────────────┐
│ 托管容器云平台（Sealos / 腾讯云 CloudBase 云托管 / 阿里云 SAE） │
│                                                               │
│   ┌───────────────────────────────────────────┐             │
│   │ 容器实例 workshop-app                        │             │
│   │ Node22 + --experimental-sqlite，监听 :3000  │             │
│   └───────────────┬───────────────────────────┘             │
│                   │ 读写                                      │
│   ┌───────────────▼───────────────────────────┐             │
│   │ 持久卷 /app/data/workshop.db（SQLite 单文件）│            │
│   └───────────────────────────────────────────┘             │
│   平台健康检查 GET /api/health → 进程异常自动重启              │
└───────┬───────────────────────────┬─────────────────────────┘
        │ 定时任务 02:00             │ 外部探活(每5–15min)
        ▼                            ▼
   backup.js(在线热备)           UptimeRobot/云监控
   上传对象存储 OSS/COS           ping 公网 HTTPS
   （跨区冗余，第二副本）         宕机→邮件/微信告警
```

## 2. 平台选型建议（待确认）

**首选：Sealos Cloud**
- K8s 托管，应用跑容器、持久卷（StorageClass）原生支持 SQLite 单文件；
- 自带监控 / 日志 / 自定义域名 / 免费 HTTPS / GitHub 一键部署；
- 国内节点、按量计费；单副本模型与 SQLite 单写者完美契合。
- 用户此前已对 Sealos 部署方式产生调研兴趣，契合度高。

**备选：腾讯云 CloudBase 云托管（云托管/CloudRun 模式）**
- 若希望留在已连通的腾讯云体系；需为容器挂 CFS/NAS 或云硬盘做持久化。
- 同样自带日志监控、自定义域名、HTTPS、CI 部署。

**不推荐**
- 裸 ECS / 轻量应用服务器：要 SSH、打补丁、自建监控 → 非真零运维；
- 海外平台：数据出境 + 延迟 + 合规风险。

**副本策略**：只跑 **1 个副本**。SQLite 是单写者，多副本会各写各文件/抢锁；可用性靠「平台自动重启 + 持久卷 + 对象存储备份」保证，不靠多副本。

## 3. 代码层改造（平台无关，确认后即可落地）

### 3.1 Dockerfile（node:22，带 --experimental-sqlite）
```dockerfile
# 零原生依赖：仅需 node:22 运行内置 node:sqlite
FROM node:22-bookworm-slim
WORKDIR /app
COPY package*.json ./
RUN npm install --omit=dev
COPY . .
# 数据库落持久卷；容器重启不丢
ENV DB_PATH=/app/data/workshop.db
RUN mkdir -p /app/data
# Node22 仍需 --experimental-sqlite 标志才能用 node:sqlite
EXPOSE 3000
CMD ["node", "--experimental-sqlite", "server.js"]
```
> 配 `.dockerignore` 排除 `node_modules/`、`data/`、`backup/`、`*.db`，避免把本地库打进镜像。

### 3.2 数据持久化
- 容器挂持久卷到 `/app/data`，设 `DB_PATH=/app/data/workshop.db`；
- 首次启动 `db.js` 自动建表 + 种子 `admin`（已知默认密码 `Wk9mP2@qL5nR#7`，上线必须改）；
- 容器平台只在 ingress 暴露 443，**内部 :3000 不在公网**（比 raw ECS 安全组更省心，前次"127.0.0.1 担忧"在此架构下天然消除）。

### 3.3 健康检查（已具备 ✅）

### 3.4 在线热备 backup.js（node:sqlite 自带 backup()，同引擎、免系统 sqlite3）
```js
// backup.js — 在线一致性备份，用 node:sqlite 的 backup()，不依赖系统 sqlite3 CLI
const { DatabaseSync } = require('node:sqlite');
const fs = require('fs'), path = require('path');
const DB_PATH = process.env.DB_PATH || path.join(__dirname, 'data', 'workshop.db');
const BACKUP_DIR = process.env.BACKUP_DIR || path.join(__dirname, 'backup');
fs.mkdirSync(BACKUP_DIR, { recursive: true });
const stamp = new Date().toISOString().replace(/[:.]/g, '-');
const dest = path.join(BACKUP_DIR, `workshop_${stamp}.db`);

const db = new DatabaseSync(DB_PATH);
db.exec('PRAGMA wal_checkpoint(TRUNCATE)'); // 先折叠 WAL，保持主库整洁
db.backup(dest);                             // 在线备份，不阻塞原库读写
db.close();
console.log('backup ok:', dest);
// 上传对象存储（按所选平台填一行）：
//   腾讯云 COS: coscmd upload dest /workshop-backup/
//   阿里云 OSS: ossutil cp dest oss://bucket/workshop-backup/
//   华为云 OBS: obsutil cp dest obs://bucket/workshop-backup/
// 失败则非零退出 → 定时任务捕获并告警
// 仅保留本地最近 3 份，防卷膨胀
const files = fs.readdirSync(BACKUP_DIR).filter(f => f.endsWith('.db')).sort();
while (files.length > 3) fs.unlinkSync(path.join(BACKUP_DIR, files.shift()));
```

### 3.5 自动 VACUUM（可选，防库长期膨胀）
- 在 backup 后偶发执行 `VACUUM`（或依赖平台定时任务每月一次），保持单文件体积可控。

## 4. 自动化部署（CI/CD，本地零操作）

- 流程：`git push main` → **GitHub Actions**（云端 runner）构建镜像 → 推镜像仓库 → 触发平台部署。
- 本地只做 `git push`；即便本机 push 偶发抖动，也可在校内重试或由平台手动触发重新部署，**CI 本身跑在 GitHub 云端，不受本机网络影响**。
- 通用工作流骨架（最终 deploy 步随平台填一行）：
```yaml
name: deploy
on: { push: { branches: [main] } }
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with: { registry: <镜像仓库>, username: ${{secrets.REG_USER}}, password: ${{secrets.REG_PWD}} }
      - uses: docker/build-push-action@v5
        with: { push: true, tags: <镜像仓库>/workshop-app:latest }
      # 平台部署（三选一，一行）：
      # Sealos:    curl -X POST ${{secrets.SEALOS_DEPLOY_HOOK}}
      # CloudBase: npx @cloudbase/cli deploy --mode container ...
      # 阿里云 SAE: aliyun sae DeployApplication ...
```

## 6. 长期稳定运行要点（2–3 年无人管）

1. **证书/域名自动续**：用平台托管 HTTPS，勿自签（避免浏览器告警 + 忘记续期）。
2. **账号与费用交接**：支付方式设稳定扣费；**账号/密码/费用到期提醒交给一位可信家人备用**——这是多年无人管最大的单点。
3. **Node 版本锁定**：Dockerfile 锁 `node:22` 基础镜像 digest，**勿随意升级**。风险点：未来 Node 小版本若移除 `--experimental-sqlite` 标志，容器启动会失败。这是唯一需前瞻的"未来断点"，可在毕业前统一评估一次升级。
4. **数据安全双副本**：持久卷（主）+ 对象存储（备，开版本/生命周期规则）；恢复用备份 db 覆盖。
5. **回滚**：保留上一镜像 tag，平台一键回滚；数据回退用备份文件。
6. **时区**：容器基础镜像确认 `Asia/Shanghai`（应用用 `datetime('now','localtime')`，错时区单号全乱）。
