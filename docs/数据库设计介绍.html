五金制造厂 ERP 工作台
数据库设计介绍

一套面向 26 人、23 台机、2 车间五金加工厂的轻量业财一体化系统。 数据库以「主数据底座 + 六大业务闭环 + 实时派生」为核心，使用 Node 内置 SQLite，零依赖、可离线部署。

存储引擎：node:sqlite（WAL） 40+ 张表 外键级联 + 实时计算 覆盖 OTC/P2P/P2D/WMS/QMS/FICO
演示材料 · 2026-08-28 · 如无远程依赖，单机/车间电脑即可运行
DESIGN PRINCIPLES

一、设计思路：四条核心原则

01主数据底座先行

  • 物料 / 客户 / 供应商 / 产品 / BOM / 机台 / 员工统一编码，作为所有业务的「锚点」
  • 先有干净的主数据，业务单据才能正确关联、追溯

02实时派生、不冗余存储

  • 库存余额、工序产量、应收/应付余额等一律用 SQL 实时聚合计算
  • 避免「多处存同一数」导致对不上——保证单一真相源

03外键 + 级联保证完整性

  • 每张表明确「删了会怎样」：明细 CASCADE、可选关联 SET NULL、防误删 RESTRICT
  • 引用关系由数据库兜底，不靠应用层记忆

04离线零依赖、可部署

  • Node 22 内置 node:sqlite，无需安装数据库服务
  • WAL + busy_timeout 抗并发写；单机/车间电脑即跑
设计哲学：「能算的就不存」 + 「关联交给外键」。把一致性责任下沉到数据库，降低业务代码的出错面。
ARCHITECTURE

二、整体架构：底座 + 六大闭环 + 派生层

存储存储引擎

  • workshop.db（SQLite，WAL 模式）
  • 单文件、零服务、易备份

底座主数据底座

  • customers / teams / machines / employees
  • products / materials / suppliers / locations

派生实时派生层

  • 库存余额、产量、MRP 净需求、毛利率
  • 均 SQL 实时算，不落表

六大业务闭环（表分组）

OTC 销售到收款 quotations → sales_orders → so_items → fg_stock_out(发货) → ar_invoices → ar_receipts
P2P 采购到付款 purchase_plans → purchase_orders → po_items → stock_in(到货) → ap_invoices → ap_payments + purchase_invoices(三单匹配)
P2D 计划到生产 boms / bom_items → production_tasks → task_operations → production_log(报工) → material_requisitions(领料)
WMS 仓储物流 stock_in / stock_out(原料) + finished_goods / fg_stock_in / fg_stock_out(成品) + locations + inventory_count(盘点)
QMS 质量管理 quality_checks(进料/过程/成品/外发回收) + outsources(外发)
FICO 财务过账 finance_ledger(成本台账) + ar_* / ap_*(资金流)

架构要点：所有闭环都挂在「主数据底座」上；业务单据实时汇向「财务（FICO）」，质量（QMS）贯穿制造全程。
SCHEMA · 主数据底座

三、核心表结构（一）：主数据底座

表用途核心字段
customers客户档案id, name(UNIQUE), type(国内/国外), owner_role(RBAC 客户隔离)
teams固定工序组枚举id, slug, name（5 组：auto/swiss/inspect/pack/mgmt）
machines机台/工位id, number(1–23 UNIQUE), team_id, status
employees员工id, emp_no(UNIQUE), name, team_id, status
products产品（五金件）id, code(UNIQUE), name, spec, unit
materials原料id, code(UNIQUE), name, safety_stock(安全库存)
suppliers供应商id, name(UNIQUE), type(材料/外协), tax_no
locations库位id, code(UNIQUE), name, area
users / sessionsRBAC 登录users(id, username, password_hash, salt, role) · sessions(token_hash, user_id, expires_at)
主数据表普遍带 UNIQUE 约束（name/code/number），从根上防止重复建档；owner_role 与 users.role 共同驱动「客户数据按角色隔离」。
SCHEMA · 业务闭环

三、核心表结构（二）：业务闭环关键表

闭环代表表核心字段（要点）
OTCsales_orders / so_itemsso_no, customer_id, status；product_id, qty, unit_price, delivered_qty(发货回写)
P2Ppurchase_orders / po_itemspo_no, supplier_id, status；material_id, qty, unit_price, received_qty
P2Dproduction_tasks / task_operations / production_logtask_no, product_id, plan_qty, sales_order_id；seq, name, team_slug；machine_id, employee_id, qty, task_id/operation_id
WMSstock_in/out · finished_goods · fg_stock_in/out · inventory_countmaterial_id/qty(+task_id 追溯)；finished_good_id/qty/source/so_id；count_no + items(book/actual/diff)

设计取舍：purchase_plans（采购计划）与 purchase_orders（已下单）分离——物料缺口阶段尚无供应商，计划实体不强迫填供应商，转单时才补，避免歪曲「已下单」语义。
RELATIONSHIPS · 外键关联

四、数据关系：以主数据为锚的关联骨架

蓝色实线：各闭环 → 主数据（引用客户/产品/物料/供应商）；绿色虚线：闭环间集成流（发货→应收、到货→应付、报工→入库、检验贯穿、发货→出库）。

级联策略（删了会怎样）

  • CASCADE明细随主表删：so_items、po_items、bom_items、task_operations
  • SET NULL可选关联置空：production_log.task_id、stock_out.task_id、quality_checks.*
  • RESTRICT防误删：outsources.supplier_id（有外发单的供应商不可删）

关键外键举例

  • sales_orders.customer_id → customers
  • bom_items.material_id → materials；qty_per × loss_rate
  • production_tasks.product_id → products；sales_order_id → sales_orders
  • ar_invoices.so_id → sales_orders；ap_invoices.po_id → purchase_orders

③应收自动生成 + 冲减

  • 登记 ar_receipts 冲减 received → 余额/状态实时重算

④应付 + 三单匹配

  • 采购到货(stock_in, po_id) → 自动建 ap_invoices(实收×单价)

WHY IT WORKS

六、设计如何支撑项目主要功能

业务闭环对应表（数据贯通）支撑的能力
OTCquotations / sales_orders / ar_*报价转单、发货、应收挂账与收款核销，老板随时看「谁欠我多少」
P2Ppurchase_plans / purchase_orders / ap_* / purchase_invoices缺料→采购→到货→应付→付款，三单匹配杜绝「票不齐就付款」
P2Dboms / production_tasks / production_log / material_requisitionsBOM→MRP→任务单→领料→报工→完工，按单追溯产量
WMSstock_*/finished_goods / locations / inventory_count原料+成品双库存、库位管理、定期盘点差异
QMSquality_checks / outsources进料/过程/成品/外发回收四类检验，质量留痕
FICOfinance_ledger / ar_* / ap_*成本按订单归集、资金流闭环、毛利率「算」出来

实时派生

  • 老板驾驶舱 / 报表随时准确
  • 不存余额，永不「对不上」

RBAC 隔离

  • users.role + customers.owner_role
  • 销售/跟单仅见自己客户

操作审计

  • audit_log 记录写操作
  • 异常不影响主流程
HIGHLIGHTS

七、设计亮点与合理性总结

✓单一真相源

  • 派生数据（库存、产量、应收应付余额）实时算，杜绝多表不一致

✓引用完整性内置

  • 外键 + CASCADE/SET NULL/RESTRICT，删除后果可预期、安全

✓轻量可部署

  • node:sqlite 零安装，车间电脑/单机即跑，单文件易备份

✓面向小厂的减法

  • 不做 MPS/APS、不冗余版本，聚焦业财一体与追溯

✓渐进演进结构

  • 计划(purchase_plans)与订单(PO)分离，不歪曲「已下单」语义

✓安全与合规

  • scrypt 密码+会话、RBAC 角色、操作审计留痕
一句话总结：用最少的存储冗余 + 最强的引用约束，把「报价→生产→发货→收款 / 缺料→采购→付款」两条资金流，以及质量与库存，全部串成一张可实时核算的关系网。这正是小厂业财一体化的关键。
