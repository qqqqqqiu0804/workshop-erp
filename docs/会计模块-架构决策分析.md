# 会计模块架构决策分析：独立系统 vs 工作台模块

> 目的：在动手实现《会计模块需求清单 v1》（柠檬云对齐版，~30 子模块、18 张新表、120 接口）之前，先回答一个前置架构问题——**这套会计能力应该作为独立系统，还是集成进现有车间工作台？**
> 结论先行：**推荐作为工作台模块集成（同服务、物理分库）**。理由见下文五维度对比与适用前提。

---

## 一、典型企业架构的两种范式

| 范式 | 代表 | 适用形态 |
|---|---|---|
| **业财一体（单系统）** | 柠檬云、金蝶精斗云、用友畅捷通、jshERP | 中小制造/贸易企业，财务与业务在同一套系统，凭证由业务单据自动生成 |
| **财务独立（多系统对接）** | 大型集团：生产 ERP（SAP/Oracle）+ 独立财务系统（用友 NC/金蝶 EAS） | 多组织、强合规、财务团队独立、审计要求物理隔离 |

**规律**：系统是否拆分，本质由**组织规模 + 合规强度 + 团队分工**决定，而非功能多少。功能多≠必须独立（柠檬云本身就把全部会计功能塞在一个 SaaS 里）。

---

## 二、五维度对比评估

> 评分说明：「模块集成」与「独立系统」两列分别给出该项下的**利弊权衡**；末尾给本项目倾向。

### 1. 业务耦合度（与工作台其他模块的依赖关系）

**证据（已核对 `db.js`）**：现有财务层已与供销业务强耦合——
- `ar_invoices.so_id → sales_orders`、`ar_invoices.customer_id → customers`
- `ap_invoices.po_id → purchase_orders`、`ap_invoices.supplier_id → suppliers`
- `finance_ledger.so_id` 关联销售订单
- `ar_receipts.ar_invoice_id → ar_invoices`（级联）、`ap_payments.ap_invoice_id → ap_invoices`（级联）

| 方案 | 利弊 |
|---|---|
| **模块集成** ✅ | 凭证可直接引用销售订单/采购订单/收付款，实现"业务单据→凭证"自动生成，这是业财一体的核心价值。无接口、无数据复制。 |
| 独立系统 ❌ | 需在两个系统间同步订单/客户/供应商主数据，要么做接口（维护成本高），要么手工重录（出错+重复）。违背"自动生成凭证"的设计目标。 |

**倾向：集成**。会计模块的上游数据源（销售/采购/生产/收付款）全部在工作台内，拆开反而破坏闭环。

### 2. 数据隔离与安全性要求

| 方案 | 利弊 |
|---|---|
| **模块集成** ⚠️ | 同库（或同服务多库）意味着账号体系、备份、权限集中。好处：RBAC 已能按角色隐藏"会计"菜单（老板/管理可见，操作员不可见）。风险：单一 SQLite 文件一旦损坏，业务+财务全丢；代账会计账号若越权可看生产数据。 |
| 独立系统 ✅ | 物理隔离更彻底：独立库、独立账号、独立备份策略，财务数据泄露不影响生产数据。适合"财务必须和运营物理分隔"的强合规场景。 |

**倾向：集成 + 缓解**。本厂规模（26 人、内网、私有仓库）下，RBAC 已满足隔离需求；"代账看全厂"风险可通过「会计账号只授财务相关角色」规避。若要做到接近独立系统的隔离，采用下方"折中方案"的分库即可。

### 3. 独立部署与扩展需求

| 方案 | 利弊 |
|---|---|
| **模块集成** ✅ | 无新增服务、端口、部署脚本。当前 `WorkshopERP` 单服务单 SQLite 已跑通开机自启；加模块=加路由+加表，零部署增量。SQLite 单文件瓶颈对两者相同。 |
| 独立系统 ❌ | 需第二个 Windows 服务、第二个端口（如 3200）、第二套备份、第二套更新流程。在仅一台闲置机的资源下是纯负担；未来若想迁更强机器，模块也能整体随服务迁移。 |

**倾向：集成**。本厂无"财务系统要单独跑在另一台服务器"的诉求。

### 4. 维护成本与团队分工

| 方案 | 利弊 |
|---|---|
| **模块集成** ✅ | 单代码库、单测试套件（现有 127 项测试可扩展）、单份部署文档、单份教学手册。当前开发者唯一，统一维护成本最低。 |
| 独立系统 ❌ | 双仓库、双 CI、双部署、双文档、双 RBAC。即便未来有专职会计开发，也可在同一仓库内按目录分工（`routes/accounting/*`），无需拆系统。 |

**倾向：集成**。拆系统只在"两个团队完全独立、发布节奏互不干扰"时才有意义，本厂暂无此情况。

### 5. 用户使用场景与权限边界

| 方案 | 利弊 |
|---|---|
| **模块集成** ✅ | 老板/管理一次登录，左侧菜单切"生产看板↔会计"， glance 生产和财务无缝。RBAC 按角色隐藏菜单，权限边界在应用内强制。 |
| 独立系统 ⚠️ | 需记第二个网址/端口、第二次登录。对"随手看一眼报表"的老板体验差；且两套权限易因不同步出现"能进 A 不能进 B"的割裂。 |

**倾向：集成**。会计的主要使用者（老板/管理/代账）本就是工作台高频用户。

---

## 三、本项目现状核对（为什么"集成"对我们有额外合理性）

1. **已有业财基础**：`finance_ledger`(P4) + `ar_*/ap_*/purchase_invoices`(P13) 已形成资金流闭环，老板/管理独享。会计模块是这套基础的**升级**（单式→复式、加科目/凭证/账簿/报表），不是从零新建。
2. **已验证的部署形态**：闲置机 `WorkshopERP` 服务 + 内网 `192.168.1.8:3100` + 开机自启 + 崩溃自愈，已稳定运行。模块继承该形态，零新增运维。
3. **RBAC 已就绪**：8 角色权限矩阵可直接扩展"会计"子模块可见性，无需重建鉴权。
4. **离线内网约束**：两系统都要离线跑，拆开不会带来"可公网独立访问财务"的好处（反而增加暴露面）。

---

## 四、推荐方案：模块集成（同服务 + 物理分库折中）

**形态**：会计模块作为工作台的一级菜单"会计"，但在存储上**使用独立的 SQLite 文件 `data/accounting.db`**，由同一 Node 服务在同一进程内加载（通过 `node:sqlite` 打开第二个 Database 句柄）。

**为什么是"折中"而非"同库"**：
- 保留模块集成全部优点（UX 一致、业财一体、零部署增量、统一 RBAC）。
- 拿到接近独立系统的隔离好处：财务数据可**单独备份/恢复**（如 `VACUUM INTO data/backups/accounting_YYYYMMDD.db`），不与业务库耦合；未来若真要拆，只需把 `accounting.db` + `routes/accounting/*` 抽离，成本低。
- 跨库引用（凭证关联销售订单）通过应用层 JOIN/二次查询实现，不建跨库外键（SQLite 不支持跨库 FK，本来就不该建）。

**落地约束（写进 v1 需求清单）**：
- 跨库事务：涉及"业务表+会计表"的写操作需手动 `BEGIN`（两库各自）+ 应用层两阶段提交，失败回滚两库（沿用现有"node:sqlite 无 transaction()"的手动事务规范）。
- 备份脚本同时备份 `workshop.db` 与 `accounting.db`。

## 五、适用前提条件（何时该改为"独立系统"）

满足以下**任意一条**时，应推翻本推荐、改为独立系统：

1. **合规隔离硬要求**：外部审计/税务要求财务数据与生产运营物理分离，或代账会计合同禁止其接触业务数据。
2. **规模跃迁**：工厂扩张到多组织/多账套，且财务团队独立、发布节奏与车间系统脱钩。
3. **数据量级突破**：会计凭证年增量达百万级、需要独立伸缩（独立服务器/独立数据库引擎如 PostgreSQL），SQLite 单文件成为瓶颈。
4. **产品化外售**：计划把会计部分作为独立 SaaS 卖给其他工厂（多租户、独立计费、独立运维）。
5. **故障域隔离需求**：财务系统宕机绝不可影响生产报工（当前同服务同进程，Node 崩则全停；若此风险不可接受，需拆进程）。

> 当前（单厂、内网、26 人、单人开发、私有仓库）**均不满足**，故推荐集成。

## 六、决策风险与缓解

| 风险 | 缓解 |
|---|---|
| 同进程崩溃牵连（会计 Bug 拖垮报工） | 会计模块路由独立、异常隔离；关键写操作加事务保护；沿用现有测试套件覆盖 |
| 代账账号越权看业务 | RBAC 给代账会计只授"会计"相关角色，不授生产/库存菜单 |
| 两库备份不一致 | 备份脚本事务性先后备份两库并记录时间戳；恢复时同时间点回滚 |
| 未来拆分成本高 | 从一开始就按 `routes/accounting/*` + `data/accounting.db` 边界清晰组织，预留抽离接口 |

---

## 七、与《会计模块需求清单 v1》的衔接

- v1 的需求范围（柠檬云对齐、~30 子模块、复式借贷、凭证/账簿/报表）**不受本决策影响**——无论集成还是独立，功能清单一致。
- 本决策只改变**承载形态**：v1 文档中"统一架构"一节应补充「同服务 + 物理分库（`accounting.db`）」作为默认实现形态，并注明上述 5 个反转前提。
- M0（会计核心骨架：科目+期间+借贷凭证+期初）按模块形态直接落地，无需等待架构拆分。

---

## 结论

**推荐：会计模块作为工作台的一级菜单集成，存储上采用同服务、独立 SQLite 文件（`data/accounting.db`）的折中隔离。**

理由：业务耦合度高（凭证强依赖销/采/生产单据）、部署资源受限（单闲置机）、维护者唯一、用户高度重叠（老板/管理）。典型企业架构中"财务独立"的拆法服务于大规模/强合规/多团队，本厂均不满足。

仅在出现合规隔离硬要求、规模跃迁、数据量级突破、产品化外售或故障域隔离需求时，才应改为独立系统——届时分库边界已预留，抽离成本低。
