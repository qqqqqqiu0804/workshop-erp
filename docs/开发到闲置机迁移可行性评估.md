# 工作台（含财务模块）本机开发 → 闲置机迁移可行性评估

> 问题：① 这套工作台（含未来会计模块）能否在本机独立开发？② 开发完成后整体迁移到闲置电脑是否简便？涵盖代码/依赖/配置/数据的可移植性，并指出关键影响因素与注意事项。
> 结论先行：**可在本机独立开发 ✅；迁移简便 ✅（架构选型决定了高可移植性）**。本厂已实测过一次整库迁移成功，本次评估基于真实架构与已踩坑。

---

## 一、本机独立开发可行性：✅ 完全可行

| 项 | 核实结果 |
|---|---|
| Node 版本 | `engines: ">=22.5.0"`；本机 managed Node `22.22.2` 满足 ✅ |
| 启动方式 | `npm start` = `node --experimental-sqlite --disable-warning=ExperimentalWarning server.js`（已自带 flag，无需手加）✅ |
| 依赖 | 仅 `express / multer / xlsx`，**全部纯 JS、无原生编译** ✅ |
| 前端 | 原生 HTML/CSS/JS，无构建、无 CDN ✅ |
| 财务模块 | 同栈，仅新增 `data/accounting.db` 一个 SQLite 文件，本机即可开发调试 ✅ |
| 端口 | 本机 3000 被 Mineradio 占用 → 开发用 `PORT=3100`；空闲机 3000 通常空闲但仍建议统一 3100，保持一致 |

**开发建议**：本机 `npm install` → `PORT=3100 npm start` → 浏览器 `http://127.0.0.1:3100`。财务模块的 `accounting.db` 由服务在首次启动时自动建库（或随迁移拷贝），无需额外环境。

---

## 二、迁移简便性评估（四维）

### 1. 代码（Code）
- **极简**：纯 JS + 原生前端，无编译、无打包产物依赖（除 `pages.bundle.js` 为预构建页面包，已随仓库携带）。
- 迁移 = **整目录复制**即可运行。
- ⚠️ 注意：若你**改过 `public/js/pages/*.js` 源码**，必须先 `npm run build:pages` 重新生成 `pages.bundle.js` 再迁移，否则目标机仍跑旧页面。

### 2. 依赖（Dependencies）
- **零原生依赖**是最大优势：`express/multer/xlsx` 均为纯 JS，`node_modules` 跨 Windows 机器**直接复制可用**，不挑 CPU/路径。
- 两种迁移方式都简单：
  - **方式 A（推荐）**：复制时连同 `node_modules/` 一起拷 → 目标机**无需联网**、无需 `npm install`。
  - **方式 B**：只拷源码，目标机 `npm install`（需联网一次，约 88 包，已实测通过）。
- 对比需要编译原生模块（如 `bcrypt`、`sqlite3`）的项目，本厂零编译，迁移难度低一个量级。

### 3. 配置（Config）
| 配置项 | 可移植性 | 说明 |
|---|---|---|
| 数据目录 | ✅ 高 | `db.js` 用 `path.join(__dirname,'data')`，**相对脚本位置**，目录搬到哪都能用 |
| 监听地址 | ✅ 高 | `server.js` 绑 `0.0.0.0`，不限本机 |
| 端口 | ✅ 高 | 经环境变量 `PORT`（默认 3000，实际用 3100），目标机设同值即可 |
| 业务绝对路径 | ✅ 无 | 应用逻辑无硬编码绝对路径 |
| **Windows 服务** | ⚠️ 路径绑定 | `nssm` 注册的 `AppDirectory` 是**绝对路径**——文件夹若搬家，旧服务指向失效，需 `uninstall` 后 `install` 重装（我们已踩过） |

### 4. 数据（Data）
- **最大优势**：SQLite 单文件，`workshop.db`（+`-wal`/`-shm`）+ 未来 `accounting.db`，复制即迁移，无需数据库服务器、无需导入导出 SQL。
- 一致做法：
  - 停服务/停 node → 拷贝 `.db`/`.db-wal`/`.db-shm` 三件套；或
  - 用 `VACUUM INTO '备份.db'`（node:sqlite 无 `backup()`，已用此法做迁移源备份）。
- 财务模块的 `accounting.db` 沿用同一机制，只是多一个文件，迁移成本几乎不变。

## 三、影响搬迁难易的关键因素

| 因素 | 影响 | 是否可控 |
|---|---|---|
| **目标机 Node ≥22.5** | 硬性前置；低于此 `node:sqlite` 不可用，迁移直接失败 | ✅ 装 Node22 LTS 即可 |
| **目录层级正确** | 曾因拷成 `workshop-app\workshop-app` 双层嵌套导致 `npm install` 找不到 `package.json` | ✅ 拷前确认单层 |
| **服务绝对路径** | 文件夹移动后旧 nssm 服务失效 | ✅ 装服务在最终位置、或重装 |
| **WAL 文件处理** | 活库直接拷可能留 `-wal` 未落盘，致数据不全/损坏 | ✅ 停进程再拷或 VACUUM |
| **端口一致性** | 本机 3100 / 目标若用 3000 会造成书签/防火墙不一致 | ✅ 统一 3100 |
| **防火墙入站** | 开发机常只本机访问；目标机需 3100 入站规则才能被平板/同事访问 | ✅ `netsh` 加规则 |
| **OS 一致性** | 当前 Windows→Windows，`.bat`/nssm 通用；若目标是 Linux 需改 systemd、无 .bat | ⚠️ 本厂不涉及 |
| **财务模块增量** | 多一个 `accounting.db` 需备份/拷贝/迁移 | ✅ 同机制，成本微增 |

## 四、注意事项（含已踩坑）

1. **目录别套两层**：从本机拷出时确认是单层 `workshop-app/`（内含 `package.json`/`server.js`/`data/`），不是 `workshop-app/workshop-app/`。
2. **`--experimental-sqlite` 不能丢**：`npm start`/服务启动命令已含；若你另写启动方式务必带此 flag，否则 `node:sqlite` 报错。
3. **别在同一台机器跑两个 node 抢 3100**：开发机手动起 + 若又装服务会 EADDRINUSE（不同机器无此问题；开发机一般只手动跑）。
4. **拷库前先停写**：停 `WorkshopERP` 服务或 node 进程，再拷 `workshop.db` 及 `-wal`/`-shm`；或用 `VACUUM INTO` 出一致性备份。
5. **node_modules 同步**：若开发机 `npm install` 过新包却只拷源码、目标机未同步，会缺依赖。建议整目录（含 node_modules）迁移最稳。
6. **服务注册在最终位置**：目标机确定文件夹落点后再 `install-service.bat`，中途移动需 `uninstall`+`install`。
7. **财务模块边界**：从一开始就按 `routes/accounting/*` + `data/accounting.db` 组织，未来若要从工作台拆出独立系统，抽离成本低（见《会计模块-架构决策分析》）。

## 五、标准迁移 SOP（对接 `deploy-idle-pc/README-迁移.md`）

**本机侧**
1. 若改过前端页面：`npm run build:pages` 重新生成 `pages.bundle.js`。
2. 停 node / 服务，确保 `data/` 静止；提交 git（可选，便于追溯）。
3. 整目录打包（含 `node_modules`、`data`）。

**目标机侧**
4. 装 Node 22.5+（已装则跳过）；解压到**单层**目录。
5. `cd` 进正确层级；`PORT=3100` 经服务脚本固化（install 脚本已设 `AppEnvironmentExtra PORT=3100`）。
6. 防火墙放行 3100 入站（`netsh advfirewall firewall add rule ...`）。
7. 先手动 `start-local.bat` / `node --experimental-sqlite server.js` 验证 `curl /api/health` 返回 `{"ok":true}`。
8. 管理员运行 `install-service.bat` 注册服务 → `sc query WorkshopERP` 显示 `RUNNING` → 重启做"不登录自启"验证。

> 本厂已于 2026-09-03 按此流程实测成功：整库迁移 + 服务化 + 开机自启 + 平板访问全部通过。财务模块加入后流程不变，仅多迁一个 `accounting.db`。

## 结论

- **本机独立开发**：完全可行，依赖与启动方式已就绪，财务模块同栈可本地调试。
- **迁移到闲置机**：**简便**。根因是架构选型（Node + node:sqlite 零原生编译、原生前端无构建、SQLite 单文件、数据目录相对路径）——对比需要数据库服务器/编译原生模块/前端构建流水线的项目，迁移成本低一个量级。
- 唯一需留心的是**路径相关项**（目录层级、nssm 绝对路径、WAL 文件、端口/防火墙一致性），均属可控的"操作纪律"而非技术障碍。
