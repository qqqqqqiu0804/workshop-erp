## D1 · 为什么用 `node:sqlite` 而不是 PostgreSQL / MySQL

### 背景

部署环境是**车间里一台常年开着的 Windows 电脑**，用的人是不懂技术的班组长和文员。数据量：员工 ~20 人、产品/物料各几百条、单据量每天几十单，三年累计十万行级别。

### 选项

| 方案 | 部署成本 | 运维成本 | 数据量上限 |
|---|---|---|---|
| PostgreSQL | 要装服务、配端口、建角色、设开机自启 | 要会看连接数、锁、VACUUM | 无实际上限 |
| MySQL | 同上，还要注意 Windows 上的编码坑 | 同上 | 无实际上限 |
| **`node:sqlite`（内置）** | **零安装**，`npm i` 后直接跑 | **零运维**，备份就是复制一个文件 | 单机够用 |

### 决定

用 `node:sqlite`（Node 22.5+ 内置），WAL 模式。

### 代价（真实付出的）

1. **必须锁死 Node ≥ 22.5**。这在 `engines` 里写死了，装低版本直接报错。如果哪天换到 Node 20 的机器，得改代码。
2. **要加 `--experimental-sqlite` 参数**。API 仍是实验性的，未来 Node 升级可能改签名——这是唯一一个"未来会咬人"的风险点，已经记在 README 的注意事项里。
3. **没有并发写**。SQLite 是单写者模型。当前场景是单机、几个用户、低频写，完全够。但如果哪天要做多车间共享，必须换库。
4. **没有网络访问**。老板想在公司看数据？只能靠"只读驾驶舱"这类页面，或者定期把 db 文件同步出去。真正多端共享时这套就不成立了。

### 换成 PostgreSQL 的条件

只要出现下面任意一条，这个决策就该被推翻：

- 需要两台以上机器同时写
- 单表超过千万行
- 需要多个车间/工厂共享一套数据
- 需要异地容灾

**当前全部不满足，所以不换。**

## D2 · 为什么前端不用框架

### 背景

用户是车间班组长，用的一台 2019 年的办公电脑和一台安卓平板。网络环境是**厂区内网，经常断**。

### 选项

| 方案 | 首屏 | 离线 | 维护 |
|---|---|---|---|
| React/Vue + Vite | 要构建，bundle 几百 KB | 要配 SW / 打包策略 | 需要 node_modules + 构建链 |
| **原生 HTML/CSS/JS** | **无构建，直接打开** | **天然离线** | 改一行刷新就生效 |

### 决定

原生 HTML/CSS/JS，**无框架、无构建、无 CDN**。

### 代价

1. **没有组件复用**。20 个页面里，"表格 + 分页 + 筛选"这套逻辑重复了很多次。后来用 `pages.bundle.js`（手动打包的公共脚本）缓解，但本质上是在手搓框架。
2. **没有响应式数据绑定**。每个页面自己写 `render()`，改数据后要记得手动重绘。有过几次"数据变了但界面没变"的 bug。
3. **状态管理靠约定**。没有 store，靠 `common.js` 里的几个全局函数。新人接手需要先读一遍。
4. **`public/js/pages/pages.bundle.js` 有 259KB**。这是手写的"打包"，里面是十几个页面的公共逻辑。它能工作，但不是好的组织方式。

### 什么情况下该换

- 页面数超过 30 个
- 需要多人同时开发前端
- 需要复杂交互（拖拽排程、实时协同）

**当前 20 个页面、单人开发、交互以表单为主，原生够用。**

## D3 · 为什么"零原生依赖"比"零依赖"更重要

### 背景

车间电脑**没有 Visual Studio Build Tools**，也没有管理员权限装东西。`npm install` 时如果某个包需要编译原生模块（node-gyp），会直接失败。

### 决定

只用**纯 JS 实现的 npm 包**。当前依赖仅 3 个：

- `express` — HTTP 框架，纯 JS
- `multer` — 文件上传，纯 JS
- `xlsx` — Excel 读写，纯 JS

**没有 better-sqlite3**（那是最常用的 SQLite 绑定，但需要编译）。这就是为什么选 `node:sqlite` —— 它是 Node 自带的，不需要编译。

### 代价

1. **放弃了成熟生态**。`better-sqlite3` 性能更好、API 更完善，但不能用。
2. **`xlsx` 有已知安全问题**（原型污染 CVE）。因为纯 JS 的 Excel 库选择很少，暂时接受，但已经限制为"只处理内网上传的可信文件"。
3. **`node:sqlite` API 比 better-sqlite3 简陋**。没有 `.pragma()` 便捷方法，得手写 SQL。

### 这条决策的真正价值

部署到一台**干净的 Windows 电脑**时，只需要：

1. 装 Node 22
2. `npm install`
3. `npm start`

**不需要装编译工具，不需要管理员权限，不会因为缺 DLL 而失败。** 这是在真实环境里被逼出来的选择，不是偏好。

## D4 · 测试怎么写：127 个用例覆盖什么

### 现状

`npm test` → **127/127 通过**，25 个测试文件，3690 行。

### 覆盖策略

| 类型 | 文件 | 覆盖什么 |
|---|---|---|
| 会计模块 | `accounting-m0..m4.test.js` | 科目、凭证、期末结转、报表勾稽 |
| 应收应付 | `ar.test.js` / `ap.test.js` | 发货自动生成应收、到货生成应付、三单匹配 |
| 权限 | `auth.test.js` / `security-rbac.test.js` | 登录、角色隔离、越权访问 |
| 主数据 | `import-masterdata.test.js` | Excel 批量导入、编码校验、重复处理 |
| 生产 | `production-stats.test.js` | 报工产量聚合、跨工序统计 |

### 为什么先测会计和权限

因为这两块**错了不会被发现**。

- 报表算错了，老板看到的是"这个月亏了"，但没人知道是 bug 还是真的亏了
- 权限错配了，销售能看到别人的客户，也不会有任何报错

而"新增一个员工"这种功能，错了用户立刻会发现。**测试要写在没有自然反馈的地方。**

### 代价

1. **没有前端测试**。UI 全靠手点，改样式时靠肉眼回归。
2. **测试跑在真数据库上**（临时文件），不是 mock。慢，但更接近真实。
3. **没有覆盖率统计**。没装 c8/istanbul，因为不想加 devDependencies。

## D5 · 为什么把文档分成四份

### 背景

第一版只有一份 README，2 万字。结果是：运维的人找不到"怎么设开机自启"，操作员看不懂"数据模型"，新人不知道从哪开始。

### 决定

按**读者**拆分，不按主题：

| 文件 | 读者 | 回答什么 |
|---|---|---|
| `README.md` | 开发者 | 架构、数据模型、API、怎么跑测试 |
| `USAGE.md` | 班组长/文员 | 每个按钮是干什么的 |
| `DEPLOY.md` | 运维 | 装在哪、怎么设 IP、怎么备份 |
| `WALKTHROUGH.md` | 新人 | 从零建档到出报表，一步步点 |

### 代价

1. **同一件事要写四遍**。加一个功能，四个文件都可能要改。
2. **容易不同步**。USAGE 里还写着旧版本的菜单名。

### 但这个代价必须付

因为**找不到文档等于没有文档**。一份 2 万字的 README，运维只会 Ctrl+F 搜"自启"，搜不到就去问老板，老板来问你。分成四份之后，每类人打开自己那份就能解决 80% 的问题。

## D6 · 已知问题与不做的事

诚实地列出**这个项目不是什么**：

| 不做 | 原因 |
|---|---|
| 多租户 / SaaS | 单厂场景，加多租户会让所有表都多一个字段，复杂度翻倍 |
| 移动端 App | 老板驾驶舱用响应式网页够了，做 App 要上架、要审核、要维护两个版本 |
| 实时协同编辑 | 车间流程是串行的（开单→报工→入库），不需要抢锁 |
| 完整财务准则合规 | 这是内部成本核算，不是对外报表，不追求会计准则合规 |
| 数据可视化大屏 | 老板要看的是"这个月赚多少"，不是一个炫酷的图 |

### 已知缺陷

- `pages.bundle.js` 是手工打包的，没有模块系统
- `node:sqlite` 的 `--experimental-sqlite` 参数未来可能失效
- 前端零测试
- 没有 TypeScript，靠 JSDoc 注释

---

## 总结：三条主线

如果只能记住三件事：

1. **部署环境决定技术选型**，不是反过来。选 `node:sqlite` 和原生 JS，都是因为"车间那台电脑装不了东西"。
2. **测试写在没有自然反馈的地方**。会计和权限错了不会有人喊，所以要测；按钮错位了有人喊，所以可以不测。
3. **文档按读者分，不按主题分**。找不到的文档等于没有文档。
