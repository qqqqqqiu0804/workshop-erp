# workshop-app 轻量化云端部署方案

> 目标：**你入学离厂后，系统能在无人现场维护的情况下长期稳定运行。**
> 技术栈维持现状不变（Node 22 + Express + SQLite），不上 NestJS、不上 PostgreSQL。
> 配套配置文件在 [`deploy/`](../deploy/) 目录，已在本机实测验证。

---

## 一、方案定位：为什么坚持轻量

你另有一个"很多人使用"的大项目，那套蓝图（NestJS + PostgreSQL + 网页端/飞书 H5 双前端 + 5 层架构）
在**它的规模下是完全正确的**。但 workshop-app 的场景不同，不能照搬：

| 维度 | 那个大项目（多人/多企业） | **workshop-app（本方案）** |
|---|---|---|
| 使用规模 | 多企业、多租户、高并发 | 单工厂 26 人，**实际峰值 5–6 人同时在线** |
| 前端 | 网页端 + 手机 H5 + 飞书（多端） | 单页 Web（原生 HTML/CSS/JS，响应式） |
| 后端框架 | NestJS（企业级分层） | Express（当前栈，不迁移） |
| 数据库 | PostgreSQL（独立服务进程） | SQLite（嵌入式单文件） |
| 部署组件 | Nginx + Node + NestJS + PG + PM2 | **Nginx + Node + systemd（3 件套）** |
| 运维人力 | 专业团队 | **你 1 人远程** |

**轻量化的三条硬理由：**

1. **SQLite 是嵌入式数据库，没有独立进程** —— 不用像 MySQL/PG 那样预留 1–2G 内存，也不用装服务、管用户权限、做时点恢复。单工厂低频场景下，WAL + `busy_timeout=5000`（`db.js:21/24`）已足够。
2. **单文件数据库 = 备份即复制** —— 整库就是一个 `workshop.db`，备份、迁移、回滚都只需操作这一个文件，灾难恢复路径极短。
3. **1 人远程维护** —— 技术栈每多一个组件，就多一份学习成本、一个故障点、一层升级负担。你不在现场，简单压倒一切。

## 二、架构

```
车间电脑 / 平板浏览器
        │
        │  HTTPS (443)
        ▼
┌──────────────────────────────────────────────────┐
│  腾讯云轻量应用服务器   2核2G / 4M / 50G SSD        │
│                                                  │
│  ┌────────────────────────────────────────────┐  │
│  │  Nginx  (443 SSL 终结)                      │  │
│  │   · 静态资源直出 public/                     │  │
│  │   · 其余请求反代 ↓                           │  │
│  └──────────────┬─────────────────────────────┘  │
│                 │ http://127.0.0.1:3000          │
│                 ▼                                │
│  ┌────────────────────────────────────────────┐  │
│  │  Node.js 22 + Express                       │  │
│  │  systemd 托管 · 崩溃自动重启 · 开机自启       │  │
│  │  业务 API / RBAC 鉴权 / 操作审计日志          │  │
│  └──────────────┬─────────────────────────────┘  │
│                 ▼                                │
│  ┌────────────────────────────────────────────┐  │
│  │  SQLite 单文件（WAL + busy_timeout=5000）    │  │
│  │  data/workshop.db                           │  │
│  └──────────────┬─────────────────────────────┘  │
│                 │ 每日 02:00  VACUUM INTO         │
│                 ▼                                │
│  ┌────────────────────────────────────────────┐  │
│  │  backup/workshop_YYYYMMDD_HHMMSS.db         │  │
│  │  本地保留 7 天                               │  │
│  └──────────────┬─────────────────────────────┘  │
└─────────────────┼────────────────────────────────┘
                  │ coscli 上传
                  ▼
        ┌──────────────────────────┐
        │  腾讯云 COS 对象存储       │
        │  异地第二副本（防硬盘损坏） │
        └──────────────────────────┘

外部探活：UptimeRobot 每 5 分钟 ping https://你的域名/api/health
          宕机即刻邮件 / 微信告警 → 你在校也能第一时间知道
```

**安全边界**：公网**只暴露 443**。应用虽绑定 `0.0.0.0:3000`，但安全组不放行 3000，
外部无法直连明文 HTTP 登录口；Nginx 通过回环地址 `127.0.0.1:3000` 访问应用。

## 四、关键实测纪要：备份为什么用 `VACUUM INTO`

**这条纠偏过一次，记录在此避免再走弯路。**

| 说法 | 实测结果（Node 22.22.2 / SQLite 3.51.2） |
|---|---|
| `DatabaseSync.backup()` 存在 | ❌ **不存在**。实例方法仅 `open / close / prepare / exec / function / location / aggregate / createSession / applyChangeset / enableLoadExtension / loadExtension` |
| `VACUUM INTO` | ✅ **可用**。实测生成 8192 字节快照，数据完整可读，耗时 0.1s |

**结论**：备份用 SQLite 原生 `VACUUM INTO`，由 `node:sqlite` 的 `db.exec()` 执行——
同引擎无版本错配、无需系统 `sqlite3` CLI、不阻塞源库读写、产出完整可用数据库。
（早前"用 `DatabaseSync.backup()` 替代 `VACUUM INTO`"的建议是错的，以此为准。）

`deploy/backup.js` 已在临时目录端到端实测通过：

```
[backup] OK workshop_20260831_103550.db 8.0KB tables=1 0.1s
```

脚本内置三项保险：① 目标文件存在则先删（`VACUUM INTO` 硬要求）；
② 备份后重新打开校验表数量与源库一致；③ 校验失败退出非零码，便于监控发现。

## 五、部署步骤

### 步骤 0：先启动备案（最早做，卡时间）
- 注册域名 → 腾讯云提交 **ICP 备案**（国内服务器强制要求）
- 工厂使用建议走**企业备案**（用营业执照），比个人备案正规
- **周期 15–20 天**，这是整个上线的关键路径，务必最优先启动
- 备案期间可先用 `http://公网IP:3000` 内网试运行（不要放行 3000 到公网，用 SSH 隧道或先跳过）

### 步骤 1：采购与网络
- 买腾讯云轻量 2核2G / 4M / 50G SSD（活动价 **99 元/年，新老同价 · 续费同价**）
- **安全组 / 防火墙入方向**：
  - `22` SSH → **只填你自己的公网 IP**，绝不 `0.0.0.0/0`
  - `80` HTTP → `0.0.0.0/0`（用于跳转 HTTPS + certbot 校验）
  - `443` HTTPS → `0.0.0.0/0`
  - ❌ **不放行 3000**
- SSH 用密钥登录，禁用密码登录

### 步骤 2：服务器初始化
```bash
bash deploy/setup.sh
```
自动完成：时区 `Asia/Shanghai`、系统更新、Node 22、Nginx、防火墙规则、目录与权限。

### 步骤 3：部署代码
```bash
cd /home/ubuntu/workshop-app
git clone <你的仓库> .      # 私有仓用 SSH deploy key
npm install
npm run build:pages        # ⚠️ 必须执行：pages.bundle.js 是构建产物，不跑前端白屏
```

### 步骤 4：托管服务
```bash
sudo cp deploy/workshop.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now workshop
curl http://127.0.0.1:3000/api/health      # 期望 {"ok":true}
```

### 步骤 5：Nginx + HTTPS
```bash
sudo cp deploy/nginx-workshop.conf /etc/nginx/sites-available/workshop
sudo ln -s /etc/nginx/sites-available/workshop /etc/nginx/sites-enabled/workshop
sudo rm -f /etc/nginx/sites-enabled/default
sudo nginx -t && sudo systemctl reload nginx

sudo apt install -y certbot python3-certbot-nginx
sudo certbot --nginx -d your-domain.com     # 证书自动续期
```

### 步骤 6：初始化数据与改密
- 全新启动：`db.js` 自动建表，默认账号 `admin / Wk9mP2@qL5nR#7`
- 迁移现有数据：把本地 `data/workshop.db` 上传到服务器同路径，`chmod 644` + `chown ubuntu:ubuntu`
- **立刻改 admin 密码**，按角色建账号（跟单 / 采购 / 品检 / 操作员），不共用老板账号

### 步骤 7：备份 + 恢复演练
```bash
# 配置每日 2:00 备份
crontab -e
0 2 * * * DB_PATH=/home/ubuntu/workshop-app/data/workshop.db BACKUP_DIR=/home/ubuntu/workshop-app/backup /usr/bin/node --experimental-sqlite --disable-warning=ExperimentalWarning /home/ubuntu/workshop-app/deploy/backup.js >> /var/log/workshop/backup.log 2>&1

# 可选 COS 异地副本：安装 coscli 后加环境变量
COS_UPLOAD_CMD='coscli cp %s cos://workshop-backup-125xxxxxxx/'
```
> ⚠️ **必须做一次恢复演练**：拿备份文件覆盖到测试库，确认能打开、数据完整。
> 只备份不验证 = 灾难时才发现备份是坏的。

### 步骤 8：外部探活告警
- UptimeRobot（免费）新建监控 `https://你的域名/api/health`，间隔 5 分钟
- 告警通知接邮件 + 微信（Server 酱 / 企业微信机器人）
- 腾讯云云监控可再配一层（CPU / 磁盘 / 流量）

### 步骤 9：验收测试
- 3–5 个账号同时登录，并行做：报工、领料发料、销售发货（自动生成应收）、采购到货（生成应付）
- 观察 `journalctl -u workshop` 有无 `database is locked`
- 手机浏览器 + 车间平板各访问一次，确认布局正常

### 步骤 10：把运维交给可信的人（你在校期间的兜底）
- 把服务器续费提醒、探活告警**同时发给一位可信家人**
- 留一份打印版《故障三件事》：重启服务 / 看日志 / 联系你
- 多年无人管的最大单点不是技术，是**续费忘了交、告警没人看**

## 七、回滚预案：随时能切回车间本地

整套系统全部业务数据就是 `workshop.db` 一个文件，这是轻量架构最大的逃生优势。

1. 云上停止访问（Nginx 返回维护页 / 安全组临时封 443）
2. 手动执行一次 `deploy/backup.js`，拿到最新完整 db
3. 把该 db 文件拷贝到车间本地电脑的 `data/workshop.db`
4. 本地 `npm start`，操作员改访问车间内网地址，恢复离线生产

> 建议车间本地保留一份可运行环境（Node 22 + 代码），**并每学期演练一次**，别只写在文档里。

| 频率 | 事项 |
|---|---|
| 自动 | 每日 02:00 备份 + COS 上传；UptimeRobot 每 5 分钟探活 |
| 每月 | 看一眼 `backup.log` 是否每天有 OK 记录；抽查 COS 上有新文件 |
| 每学期 | 恢复演练一次（拿最新备份还原到测试库）；`apt upgrade` 打系统补丁 |
| 每次改代码 | 先手动备份 → 拉代码 → `npm install` → `npm run build:pages` → `systemctl restart workshop` |

排查命令：
```bash
sudo systemctl status workshop
sudo journalctl -u workshop -f
sudo journalctl -u workshop --since today | grep -i 'locked\|error'
tail -f /var/log/workshop/backup.log
```

## 十、已知风险与限制

| 风险 | 说明 | 缓解 |
|---|---|---|
| **工厂外网中断** | 外网一断系统全瘫，报工/领料停摆 | 车间保留本地可运行环境 + 每学期演练回滚 |
| **单台 ECS 单点** | 云主机故障需等厂商恢复 | COS 异地备份保数据；服务层接受此风险（轻量方案固有） |
| **SQLite 写并发上限** | 5–6 人并发下余量充足；**未来若扩车间/招人需重新评估** | WAL + busy_timeout 已兜底；验收测试验证；真扛不住再升配或迁 PG |
| **`--experimental-sqlite` 标志** | 未来 Node 若移除该 flag，服务会启动失败 | 镜像/版本锁 Node 22；升级 Node 大版本时先验证再切 |
| **公网暴力扫描** | 持续被扫密码 | 登录失败锁定已内置（`auth.js`）；全员强密码 |
